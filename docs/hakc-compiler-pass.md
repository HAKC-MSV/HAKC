# HAKC Compiler Pass Documentation

After building LLVM, the HAKC pass is used by either of the following:

1. Start the policy server
    * Create a policy server config file based on
      `configs/policy-server/hakc-policy-server.yml`
    * `python3 -m venv python/venv`
    * `source python/venv/bin/activate`
    * `python3 -m pip install -r llvm-project/llvm/utils/hakc/requirements.txt`
        * This install step only needs to happen once
    * `python3 llvm-project/llvm/utils/hakc/hakc-policy-process --config 
   <path/to/policy/server/config>`

2. If the pass mode is set to `RunCompartmentalization`, the policy server must be
   started. If the pass mode is set to `RunDataAccessGraphAnalysis`, the policy server
   does not need to be running. Invoke the pass using one of the following methods:
    1. `clang -g -mllvm --enable-hakc -mllvm 
   --hakc-config=<path/to/compartmentalization/config> <path/to/source>`
        * The pass requires debug information to properly find types
    2. `opt -passes=hakc --hakc-config=<path/to/compartmentalization/config> 
   <path/to/LLVM/IR>`

The source for the HAKC pass is in
[
`llvm-project/llvm/lib/Transforms/Compartmentalization/hakc`](../llvm-project/llvm/lib/Transforms/Compartmentalization/hakc).

The HAKC pass communicates with the policy server over a named socket, provided in the
policy server config as `socket_path` and in the HAKC config as `Database.server-url`. The
policy server can consume a compartmentalization policy in a yaml format, and example of
which can be found in
`cmake-build-hakc-llvm/llvm-project/llvm/test/Transforms/Compartmentalization/hakc/tests/hakc_test0/db.yml`.
However, for large projects a graph database will likely be faster. We are using
the [Kuzu graph database](https://docs.kuzudb.com/) for our database, since it has wide
support for many different languages.

HAKC compartmentalizes software in two phases. First, HAKC finds all symbols and types
used in an application. This is triggered by setting the `PassMode` in the HAKC config to
be `RunDataAccessGraphAnalysis`. This process generates one file per compilation unit that
end in `.dag.yml` under the directory listed in
`DagAnalysisRootPath` in the HAKC config. Once the `.dag.yml` files are generated, a Data
Access Graph (DAG), which is a directed graph that contains all symbols and their
interactions with other symbols needs to be created. Creating the DAG is done by invoking
[

like so:

* `python3 llvm-project/llvm/utils/hakc/hakc-static-analysis --dag-files-root 
<DagAnalysisRootPath> --create-dag --db-dir <path/to/policy/server/path>`

When that is done, a base compartmentalization policy is stored in the database. This
policy places each symbol in its own compartment. However, that will likely not work in
practice, and adjustments to the policy will need to happen. Adjustments can be made like
so:

* `python3 llvm-project/llvm/utils/hakc/hakc-static-analysis 
  --db-dir <path/to/policy/server/path> 
   --adjust --adjust-path <path/to/adjustments.yml>`

The `adjustments.yml` encodes which compartments symbols belong to. An example of an
adjustment file is
[
`configs/compartmentalizations/linux/adjustments/linux-x86-adjustments.yml`](../configs/compartmentalizations/linux/adjustments/linux-x86-adjustments.yaml).
Once the final compartmentalization policy is generated by adjusting the DAG, enforcement
of the policy can be done.

The final phase of compartmentalization is done by recompiling the application with
`PassMode` in the HAKC config set to `RunCompartmentalization`. Ensure that the policy
server is running, and recompile the application to add in enforcement.
